我同時使用 Claude、Codex、Antigravity 與 Hermes，但我不把它們當成四位可以自由改動所有內容的「全能助理」。對我而言，更安全的做法是把它們安排成一個有角色、有交接規則，也有最終負責人的研究團隊。

> **先說結論**：AI 分工的目的不是找出「最強模型」，而是讓每個任務都有明確負責者、輸入、輸出與查核方式。任何重要研究判斷，最後仍由研究者負責。

## 為什麼不要四個 AI 同時做同一件事？

生成式 AI 確實可能提高效率。Noy 與 Zhang（2023）在 453 名受試者的寫作實驗中發現，使用 AI 的參與者平均完成得更快，成品評分也較高。不過，AI 的幫助不是每個任務都一樣。Dell’Acqua 等人（2026）把這種現象稱為「鋸齒狀技術前沿」：有些看起來很難的工作，AI 做得很好；另一些看似相近的工作，AI 卻可能讓人更容易答錯。

如果四個 AI 同時修改同一個 GitHub repo、HackMD 筆記或 Skill，常見結果不是四倍效率，而是：

- 同一段文字被不同版本覆蓋。
- 一個 AI 刪除另一個 AI 剛新增的設定。
- 分析條件改了，README 卻仍保留舊說明。
- 每個 AI 都以為另一個已經查核文獻。
- 最後無法回答「這個結論是誰決定的」。

這不只是技術問題，也與自動化偏誤有關。系統性回顧顯示，人可能因過度相信自動系統而採納錯誤建議，或因系統沒有提醒就漏做必要動作（Goddard et al., 2012）。因此，多 AI 工作流必須比單一聊天更重視責任與紀錄。

## 我的四個工具怎麼分工？

以下不是四個產品的永久能力排名，而是我為自己的研究環境設定的角色。

| 工具 | 我安排的主要角色 | 適合交付的成品 | 不讓它單獨決定的事 |
|---|---|---|---|
| Claude | 研究內容編輯與批判性討論 | 文章架構、研究問題、段落改寫、方法限制清單 | 最終引用、統計結論、直接發布 |
| Codex | 程式、Git 與可驗證實作 | 分析程式、測試、README、網站修改、版本紀錄 | 未經驗證的研究推論 |
| Antigravity | 視覺化開發與互動檢查 | dashboard、介面原型、瀏覽器測試、圖表呈現 | 原始資料的不可逆修改 |
| Hermes | 長期運作與定時傳送 | Telegram 文獻簡報、排程、日常提醒、背景任務 | 未查核文獻直接進入正式論文 |

這個分工的核心是：**Claude 幫我想清楚，Codex 幫我做得可驗證，Antigravity 幫我看見成品，Hermes 幫我持續執行。** 四者可以互相補位，但不能同時擁有同一份檔案的寫入權。

## 一個實際例子：寫 HRV 科普文章

我可以把工作拆成以下流程：

1. 我先決定文章問題，例如「腕式 PPG 得到的 BBI 能不能直接當成 ECG 的 RR interval？」
2. Claude 協助整理讀者會困惑的概念與文章架構。
3. 文獻必須透過資料庫、DOI 或原始全文核對，而不是相信聊天模型列出的引用。
4. Codex 把核對後的內容寫進網站、檢查文章路由、搜尋與 Markdown 顯示。
5. Antigravity 或瀏覽器測試負責查看手機與桌面版，確認圖表和文字是否容易閱讀。
6. Hermes 之後可以定期蒐集新文章，但只進入「待閱讀」，不會自動改寫已發布結論。

這樣做的好處是，每一步都有不同的成功標準。文章寫得流暢不代表引用正確；程式能執行不代表統計方法合理；網站能打開也不代表研究解釋沒有過度推論。

## 避免 AI 打架的五條規則

### 1. 同一時間只有一個寫作者

同一個 branch、檔案或 HackMD 筆記，只指定一個 AI 修改。其他 AI 只能讀取、評論或提出 patch 建議。

### 2. 每次交接都留下四項資訊

```text
任務：這次要完成什麼？
輸入：使用哪些檔案、文獻或資料版本？
輸出：改了哪些檔案、產生哪些結果？
未決事項：哪些內容還沒有查核或需要我決定？
```

### 3. GitHub 是程式版本的裁判

AI 說「已經改好」不算完成。必須能在 Git diff 中看見修改、通過測試、留下清楚 commit，並確認遠端與網站版本一致。

### 4. 文獻存在不代表支持該句話

Walters 與 Wilder（2023）發現，早期 ChatGPT 版本產生的引用中有相當比例是捏造或帶有書目錯誤。即使 DOI 存在，也要打開全文確認研究設計、樣本及結果是否真的支持文章中的句子。

### 5. 最終決策不能委託

研究問題、排除標準、主要結果、因果解釋、作者署名與是否公開，必須由研究者決定。AI 可以提出選項，但不能替我承擔學術責任。

## 我如何判斷任務交給誰？

先問三個問題：

1. 這是內容理解、程式實作、視覺檢查，還是長期排程？
2. 結果能不能用測試、DOI、原始輸出或畫面驗證？
3. 如果做錯，能不能用 Git 或備份恢復？

如果答案不清楚，我會先讓 AI 做唯讀分析，不直接修改。如果涉及研究資料、公開發布或 Git 歷史改寫，則提高人工確認層級。

## 帶走三個重點

1. 多 AI 的價值來自角色清楚，不是工具數量。
2. 每一個 AI 交付物都要有外部可驗證依據。
3. 我是整個工作流的研究負責人，AI 是具有不同介面的協作工具。

> **一句話總結**：最好的 AI 研究團隊不是四個 AI 同時回答，而是每一步都知道誰在做、依據什麼、由誰查核。

## 為什麼以任務分工，而不是以模型品牌分工？

Noy 與 Zhang（2023）的隨機實驗顯示，生成式 AI 能改善特定專業寫作任務的完成時間與品質。然而，Dell’Acqua 等人（2026）對 758 名知識工作者進行預先註冊實驗，發現 AI 在能力邊界內提高工作量、速度與品質，但在邊界外的複雜任務中，使用 AI 的參與者反而較不容易得到正確答案。

這表示「AI 是否有用」不是工具層級的固定屬性，而是工具、模型、輸入品質、任務類型、驗證條件與使用者專業共同形成的結果。因此，我不宣稱 Claude 天生只適合寫作、Codex 只適合程式。我的做法是依**當前介面可以留下什麼可驗證產物**來分工。

## 四層角色架構

| 層級 | 主要工具 | 任務邊界 | 必要證據 | 完成條件 |
|---|---|---|---|---|
| 研究推理與編輯 | Claude | 問題拆解、論證、反方觀點、文字結構 | DOI、全文定位、使用者提供的研究材料 | 未核對主張被明確標示 |
| 執行與版本化 | Codex | 程式、測試、Git、網站與可重現腳本 | diff、測試輸出、commit、檔案雜湊 | 工作樹清楚且可重跑 |
| 互動與呈現 | Antigravity | IDE 實作、瀏覽器檢查、dashboard、介面原型 | screenshot、DOM/console、視覺檢查 | 桌機與手機主要流程可用 |
| 持續運作 | Hermes | gateway、Telegram、cron、例行蒐集與提醒 | 執行紀錄、排程、訊息送達 | 任務可重複執行且失敗可觀察 |

Claude Code 的官方文件描述其可跨專案讀取檔案、協調修改並執行測試；Codex 是可在程式環境中讀取、修改與執行程式的 coding agent；Antigravity IDE 支援 agent panel、Skills、MCP 與瀏覽器驗證；Hermes 則提供持續記憶、gateway、訊息平台及背景運作。這些功能支持角色配置，但不構成模型品質的直接比較。

## 核心治理原則：Single-writer, multiple-reviewers

同一項 artifact 在同一時間只允許一個寫作者。其他代理可以提出 review，但不能在未同步的情況下直接改寫。這條規則適用於：

- Git branch 與網站文章。
- HackMD 方法筆記。
- 共用 `SKILL.md`、`AGENTS.md` 或 `CLAUDE.md`。
- 統計分析腳本與輸出表。
- Hermes 的排程與主題設定。

若需要平行工作，應拆成彼此獨立的 artifact，例如由一個代理檢索來源、另一個代理檢查程式，但兩者不能各自在相同分析檔案中「順便修正」。整合者必須逐項接受或拒絕變更。

## 標準交接封包

每次跨工具交接都應包含：

```yaml
task_id: hrv-article-2026-08
objective: 說明 PPG、BBI 與 RR interval 的關係
owner: codex
inputs:
  - source_manifest.md
  - posts/garmin-raw-data-hrv.md
constraints:
  - 不新增未驗證引用
  - 不修改其他文章
outputs:
  - revised_markdown
  - route_test_result
verification:
  - DOI resolution
  - git diff review
  - browser rendering
open_issues:
  - PPG artifact threshold 尚未確認
```

這種封包把「上下文」變成可追蹤資料，而不是只存在聊天紀錄。它也降低代理切換後自行補猜研究設計的風險。

## 研究任務的風險分級

| 風險 | 範例 | AI 權限 | 人工閘門 |
|---|---|---|---|
| 低 | 格式化 Markdown、搜尋檔案、產生草稿標題 | 可自動執行 | 抽查 diff |
| 中 | 重構分析程式、整理文獻表、修改網站 | 可執行但需測試 | 合併前審查 |
| 高 | 排除參與者、選主要模型、解釋因果、公開未發表結果 | 只能提出方案 | 研究者明確決定 |
| 極高 | 刪除資料、改寫 Git 歷史、上傳個資、使用憑證 | 預設禁止或逐次授權 | 精確目標與復原／撤銷方案 |

## 自動化偏誤與責任擴散

Goddard 等人（2012）的系統性回顧指出，自動化偏誤可表現為接受錯誤建議的 commission error，或因系統未提醒而未執行必要行動的 omission error。多代理環境還增加另一項風險：每個代理都產生看似合理的片段，但沒有人對整體一致性負責。

Messeri 與 Crockett（2024）進一步提醒，科研 AI 可能帶來「理解錯覺」：研究者把系統可產生流暢解釋，誤認為自己已掌握機制；也可能因工具擅長處理某類問題，而不自覺縮窄研究問題。對我的工作流而言，對策不是禁止 AI，而是要求每個重要結論都回答：

1. 來源是資料、文獻、政策，還是 AI 建議？
2. 哪一個 artifact 保存了證據？
3. 哪個人批准了研究決策？
4. 如果模型改版，結果能否重新生成？

## 防止 Claude 與 Codex 修改衝突

我採用以下操作規則：

1. 開工前先執行 `git status` 與 `git fetch`。
2. 每個任務使用明確 branch 或 worktree。
3. AI 不得覆蓋來源不明的未提交修改。
4. 一個 Skill 只設定一個 canonical location；其他平台使用連結或同步腳本，不複製後各自修改。
5. commit 必須描述變更目的，不能只寫「AI update」。
6. 發布前比較本機、遠端與 GitHub Pages 的實際版本。

## 任務路由決策

```text
是否需要長期排程或手機訊息？ ── 是 → Hermes
                 │
                 否
                 ↓
是否主要修改程式、Git 或網站？ ── 是 → Codex
                 │
                 否
                 ↓
是否主要需要視覺原型與瀏覽器互動？ ── 是 → Antigravity
                 │
                 否
                 ↓
研究論證、內容結構與批判性整理 → Claude／人工研究者
```

這只決定「第一責任工具」，不是禁止其他工具 review。當任務跨層時，以交接封包傳遞，不把全部權限同時打開。

## 完成定義

一項 AI 研究任務只有同時滿足以下條件才算完成：

- 交付物有確定路徑與版本。
- 中央主張可連到來源或分析輸出。
- 程式可執行並保存環境與參數。
- 已知限制與未決事項沒有被流暢文字掩蓋。
- 公開內容不含 token、個資或未授權材料。
- 人類研究者完成最終科學判斷。
