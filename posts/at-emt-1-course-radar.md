每次要找緊急救護技術員（EMT-1）複訓或運動傷害防護員（AT）繼續教育課程，我都得在不同學會、協會、學校與報名平台之間來回搜尋。課程資訊分散，標題與日期格式又不一致，很容易錯過適合的課程或報名期限。

因此，我建立了「AT & EMT-1 進修課程雷達」：由程式定期整理公開課程，再集中呈現在一個可以搜尋、篩選、查看行事曆與連回原始公告的網站。

👉 **[立即體驗：AT & EMT-1 進修課程雷達 ↗](https://at-emt-1-course-radar.vercel.app/)**

> 這個網站是資訊整理工具，不是官方報名或積分認證平台。日期、費用、名額、資格、時數與積分認列，仍應以主辦單位最新公告為準。

## 為什麼需要一個「課程雷達」？

我同時具有運動傷害防護員與 EMT-1 證照，也正在進行認知神經科學研究。對需要持續進修的專業人員而言，真正耗時的往往不是「沒有課」，而是：

- 不知道課程公布在哪一個平台；
- 同一個平台混有初訓、複訓、長照或其他不相關課程；
- 有些日期使用民國年，有些使用西元年；
- 課程可能分成多個上課日，標題卻只顯示部分資訊；
- 報名期限、名額與課程狀態可能隨時改變；
- 找到課程之後，還得自己重新整理到行事曆。

課程雷達不是取代原始公告，而是先完成「找得到、看得懂、能比較」這一段工作，再把讀者送回主辦單位完成確認與報名。

## 現在可以怎麼使用？

### 1. 搜尋與多條件篩選

可以用課程名稱、主辦單位、來源或地點搜尋，也能依運動防護／EMT、地區、線上課程、近期開課及資料完整度等條件縮小範圍。過期課程可隱藏，但仍能在需要時重新查看。

### 2. 清單與行事曆兩種視角

清單適合快速比較課程；月曆適合判斷時間是否衝突。點選日期後，可看到當天收錄的課程，再開啟完整資訊。

### 3. 課程詳情與原始公告

課程詳情會盡可能整理日期、時間、地點、費用、時數、積分、報名期限、狀態、主辦單位與資訊來源。最後仍提供「查看原始公告與報名」連結，讓使用者完成最後查核。

### 4. 加入行事曆與分享

有明確日期的課程可以下載 `.ics` 行事曆檔，加入手機或電腦行事曆；也能複製特定課程的連結，傳給同事或同學。

### 5. 資料來源透明化

網站另有「資料來源」頁，讓使用者知道目前追蹤哪些公開平台。來源數量會隨維護狀況調整，因此文章不再把系統限制成固定的「六大平台」。

## Vercel 與 Supabase 分別做什麼？

可以把整個系統想成一間小型圖書館：

| 工具 | 白話角色 | 在本專案負責的工作 |
|---|---|---|
| Python／自動化流程 | 館員 | 定期找新課程、解析網頁、整理欄位與排除雜訊 |
| Supabase | 書庫與門禁 | 用 PostgreSQL 保存結構化課程，並限制誰能讀取或修改 |
| Vercel | 閱覽室與門面 | 將網頁快速發布，讓手機與電腦都能開啟課程雷達 |
| 瀏覽器 | 使用者的桌面 | 搜尋、篩選、顯示月曆，並記住本機偏好 |

Vercel 並不取代 Supabase：前者負責把網站送到讀者面前，後者負責保存與管理資料。兩者透過部署設定與資料載入流程合作。

## 為什麼還需要「靜態快照」？

課程雷達保留兩種資料讀取方式：

1. **遠端讀取**：前端在允許時，使用公開、唯讀的金鑰向 Supabase Data API 取得最新資料。
2. **靜態快照**：部署時把最近一次整理完成的課程資料一起放進網頁；即使資料庫暫時無法連線，網站仍可顯示內容。

截至本文查核的公開版本採「靜態快照優先」。這不表示 Supabase 沒有參與，而是把資料庫與一般訪客隔開一層，降低臨時斷線、額度或跨網路請求對閱讀體驗的影響。未來若需要更即時的更新，也能切換到 Supabase 的唯讀遠端模式。

## 從公開網頁到一筆可用資料

一門課程進入網站前，大致會經過以下步驟：

1. 自動化程式讀取各來源的公開頁面；
2. 找出可能是 AT 或 EMT-1 進修的內容；
3. 將民國日期轉成一致的西元 `YYYY-MM-DD`；
4. 整理課程名稱、地點、費用、時數、積分與報名狀態；
5. 用穩定識別碼判斷是否為既有課程，避免重複新增；
6. 寫入 Supabase，並產生可供 Vercel 使用的最新快照；
7. 使用者在網站中篩選後，再回到原始公告完成確認。

自動整理能降低搜尋成本，但無法保證理解每一個主辦單位的特殊寫法。因此，網站刻意保留來源連結與免責提醒，而不是把整理結果包裝成官方資料。

## 我從這個專案學到什麼？

這個專案不只是做一個課程清單，而是把自己的專業痛點轉成一套可維護的資料產品。我必須同時思考：哪些資料值得收錄、如何處理錯誤日期、怎麼避免重複、公開網站可以看到哪些資料，以及資料庫暫時失效時網站是否仍能使用。

對我而言，AI 與自動化最有價值的地方不是取代專業判斷，而是把重複搜尋與格式整理交給系統，讓人把時間留給課程內容、資格確認與實際學習。

「AT & EMT-1 Course Radar」是一個以公開進修資訊為資料來源、採靜態網站與雲端資料庫混合架構的輕量資料產品。它將資料擷取、正規化、儲存、發布與前端查詢分離，使各層可以獨立更新，也降低單一服務失效時整個網站不可用的風險。

## 系統目標與非目標

系統的核心目標是縮短 AT 與 EMT-1 專業人員發現課程、初步比較及回到原始公告的時間。它不是報名代理、積分審查系統，也不判定某課程必然符合個人的換證或繼續教育需求。

因此，資料模型與介面優先保留 `source`、`url`、`organizer`、`status`、`credits` 等可追溯欄位，而不是只留下課程名稱與日期。任何自動推論都應能回到來源頁再次核對。

## 整體架構

```text
公開課程頁面
  │
  ▼
Python 擷取器與來源別解析規則
  │  日期正規化／欄位清洗／分類／去重／驗證
  ▼
Supabase PostgreSQL
  │  受限的公開讀取 + 僅限後端的寫入權限
  ├──────────────► 可選：PostgREST / Data API 唯讀載入
  │
  ▼
建置／匯出最新資料快照
  │
  ▼
Vercel 靜態部署
  │  HTML + CSS + JavaScript + fallback snapshot
  ▼
使用者瀏覽器：搜尋、篩選、月曆、詳情、ICS、分享
```

這不是「Vercel 或 Supabase 二選一」，而是兩個不同責任層：Supabase 管理資料與存取控制；Vercel 提供版本化部署、公開網址與靜態資源傳遞。

## 資料擷取、清洗與去重

不同來源無法共用完全相同的解析器。有些頁面提供結構化課程列表，有些將多個日期寫在同一段標題，也有些只在文字中描述費用、時數或截止日。因此流程採「共通欄位 + 來源別規則」：

- 以關鍵詞及排除詞先降低不相關結果；
- 將 `115/8/20`、`115年08月20日` 等民國日期轉成西元日期；
- 將同一課程的多個上課日拆分或建立系列關聯；
- 盡可能解析 `start_time`、`end_time`、`price`、`hours`、`credits`、`registration_deadline` 與 `status`；
- 對來源 ID 不穩定的頁面建立可重現的雜湊識別碼；
- 寫入前驗證必要欄位，並以主鍵 upsert，避免每次排程都新增重複資料。

資料清洗的原則不是「猜滿所有欄位」。若原始公告沒有清楚資訊，寧可保留空值或標記需回原文確認，也不應由模型自行補出日期、積分或費用。

## Supabase：資料層與權限邊界

Supabase 提供 PostgreSQL 與 Data API，適合保存結構化課程並透過 REST 查詢。以下是概念化、經簡化的資料結構；實際資料可依來源包含更多選填欄位：

```sql
create table public.courses (
  id text primary key,
  title text not null,
  url text not null,
  date date,
  source text not null,
  organizer text,
  query_keyword text,
  start_time text,
  end_time text,
  location text,
  registration_deadline date,
  price text,
  hours text,
  credits text,
  status text,
  summary text,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);
```

### RLS 不等於「只要打開就安全」

資料表應啟用 Row Level Security（RLS），並同時檢查 PostgreSQL grants 與 policies。公開網站只需要讀取已公開課程，因此前端角色只應獲得 `SELECT`；新增、修改與刪除則保留給自動化後端。

```sql
alter table public.courses enable row level security;

revoke all on table public.courses from anon, authenticated;
grant select on table public.courses to anon;

create policy "public courses are readable"
on public.courses for select
to anon
using (true);
```

這段只是概念範例，正式設定仍須依實際的 schema、key 類型與 Supabase 專案權限測試。特別重要的是：

- 瀏覽器只能使用 Supabase 的 **publishable key**，或舊版專案的 `anon` key；它們必須搭配正確的 RLS 與最小權限。
- **secret key** 或舊版 `service_role` key 具有高權限、可繞過 RLS，只能存在受保護的後端或自動化祕密設定，不能寫進 HTML、JavaScript、截圖或公開 GitHub repo。
- Supabase 已以 publishable／secret keys 取代舊式 `anon`／`service_role` 命名；維護舊專案時應留意官方遷移時程。

官方參考：[Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)、[Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)、[Securing your data](https://supabase.com/docs/guides/database/secure-data)。

## Vercel：展示、部署與環境設定

Vercel 負責發布 HTML、CSS、JavaScript 與建置時產生的資料快照。對這類不需要會員登入的公開查詢網站，靜態部署有幾個優點：首屏快速、維護成本低、可依每次部署回復版本，而且資料庫短暫不可用時仍可閱讀上一次成功匯出的內容。

若建置流程需要 Supabase URL 或金鑰，應在 Vercel Project Settings 的 Environment Variables 管理，並區分 Production、Preview 與 Development。環境變數更新只會套用到之後的新部署，不會自動改變既有部署。

但環境變數不是把前端祕密藏起來的魔法：任何被編譯進公開 JavaScript 或送到瀏覽器的值，使用者都能查看。因此前端只能放 publishable／anon 等低權限金鑰；高權限 secret／service role key 必須留在伺服器端或 GitHub Actions secrets。

官方參考：[Vercel Environment Variables](https://vercel.com/docs/environment-variables)、[Vercel Environments](https://vercel.com/docs/deployments/environments)。

## 混合式資料載入策略

前端的資料選擇邏輯可概括為：

```js
if (preferRemote && supabaseUrl && publishableKey) {
  // 以唯讀權限查詢 Supabase；逾時或失敗則回退
  courses = await loadFromSupabase().catch(() => fallbackSnapshot);
} else {
  courses = fallbackSnapshot;
}
```

目前公開部署採快照優先：設定中沒有將資料庫憑證暴露給瀏覽器，畫面直接使用最近一次成功產生的課程快照。系統仍保留遠端查詢能力，因此未來可以依更新頻率、流量、額度與穩定性需求調整。

| 模式 | 優點 | 代價與風險 |
|---|---|---|
| Supabase 即時唯讀 | 資料更新後可立即顯示，不必重新部署 | 依賴網路、RLS、API 可用性與額度；需處理逾時與錯誤 |
| Vercel 靜態快照 | 穩定、快、沒有每位訪客都查資料庫的成本 | 更新後需重新產生快照／部署，內容可能有時間差 |
| 混合模式 | 即時讀取失敗時仍有內容 | 邏輯與測試較複雜，必須清楚標示資料更新時間 |

## 前端資料產品功能

目前前端不是單純把 JSON 印成卡片，而是把資料轉成幾個可操作的視角：

- **搜尋與篩選**：依文字、專業類別、地區、近期、線上／實體及資料品質過濾；
- **月份分組**：讓大量課程仍能快速掃讀；
- **月曆模式**：按日期檢視課程並處理月份切換；
- **課程詳情**：集中呈現可解析欄位，並保留原始公告；
- **ICS 匯出**：將日期、時間、地點、說明與 URL 轉成行事曆事件；
- **深層連結與分享**：以網址參數開啟指定課程；
- **本機偏好**：使用 `localStorage` 記住篩選條件與看過的課程，不要求建立帳號；
- **資料品質提示**：指出缺少日期、地點或其他重要欄位的項目。

前端也需處理不可信字串。課程名稱、地點與摘要來自外部網站，輸出到 HTML 前必須跳脫；外部連結要限制為安全的 `http`／`https` URL，避免把抓到的內容直接當成可執行標記。

## 自動更新與故障處理

理想的排程不是「爬蟲跑完就算成功」，而應留下可檢查的狀態：

1. 排程啟動並記錄本次執行時間；
2. 各來源分別擷取，單一來源失敗不應讓全部資料歸零；
3. 驗證課程數量、重複 ID、日期範圍及必要欄位；
4. 通過品質閘門後才 upsert Supabase；
5. 匯出靜態快照並觸發 Vercel 新部署；
6. 部署後檢查首頁、資料筆數、更新時間與原始連結；
7. 失敗時保留上一個可用版本並發送通知。

需要特別避免「成功執行但產生空資料」：爬蟲可能因來源版面變動而沒有報錯，卻抓不到任何課程。因此課程筆數突然大幅下降、來源歸零或未來日期全部消失，都應視為需要人工檢查的異常。

## 隱私、授權與資訊責任

網站目前不要求登入，篩選偏好主要保存在使用者自己的瀏覽器。課程資訊取自公開公告，但公開不等於可以任意重新授權；網站應保留來源、採摘要與導流方式呈現，並提供錯誤更正與下架聯絡管道。

自動分類、AI 摘要與資料清洗都可能出錯，因此介面需要持續提示：收錄不代表推薦或認證，報名、付款、資格、課程異動與積分認列均以主辦單位最新公告為準。

## 下一步可以怎麼改進？

- 為每一個來源增加擷取成功率、最後成功時間與欄位完整度監測；
- 對 RLS、公開讀取、禁止匿名寫入建立自動化測試；
- 在部署前比較新舊快照，阻擋異常大量刪除；
- 為 Supabase 遠端模式加入明確逾時、快照 fallback 與資料版本標示；
- 建立使用者回報錯誤的 issue 表單，但避免蒐集不必要個資；
- 保存來源解析器與資料 schema 的版本，讓資料變更可追溯；
- 對行動裝置、鍵盤操作、對比與螢幕閱讀器持續進行無障礙測試。

這套架構的重點不是使用多少雲端工具，而是讓每一層責任清楚：爬蟲負責蒐集，Supabase 負責資料與權限，Vercel 負責部署，瀏覽器負責互動，而最終的專業判斷仍回到使用者與原始公告。
